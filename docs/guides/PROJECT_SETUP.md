# Project Setup Guide

> Configure your project structure for optimal use with project-mcp.

## Overview

project-mcp works with two main directories:

| Directory   | Purpose                 | Contents                          |
| ----------- | ----------------------- | --------------------------------- |
| `.project/` | Operational tracking    | Status, tasks, roadmap, decisions |
| `docs/`     | Reference documentation | Guides, API docs, architecture    |

## Recommended Structure

```
my-project/
├── .project/                    # Project management (operational)
│   ├── index.md                 # Contract file
│   ├── BACKLOG.md               # Prioritized work queue
│   ├── TODO.md                  # Task dashboard
│   ├── ROADMAP.md               # Project roadmap
│   ├── STATUS.md                # Current status
│   ├── DECISIONS.md             # Architecture decisions
│   ├── todos/                   # Active tasks (YAML files)
│   └── archive/                 # Completed tasks
│
├── docs/                        # Documentation (reference)
│   ├── README.md                # Documentation index
│   ├── architecture/            # System design docs
│   │   ├── README.md
│   │   ├── OVERVIEW.md
│   │   └── COMPONENTS.md
│   ├── api/                     # API reference
│   │   ├── README.md
│   │   └── ENDPOINTS.md
│   ├── guides/                  # User guides
│   │   ├── README.md
│   │   └── GETTING_STARTED.md
│   ├── reference/               # Technical reference
│   │   ├── README.md
│   │   └── CONFIGURATION.md
│   └── releases/                # Release notes
│       ├── README.md
│       └── RELEASE_NOTES_v1.0.0.md
│
├── README.md                    # Project overview
├── CONTRIBUTING.md              # Contribution guidelines
└── .mcp.json                    # MCP configuration
```

## Setting Up .project/

### Initialize with init_project

The fastest way to set up:

```json
{
	"tool": "init_project",
	"arguments": {
		"project_name": "My Application",
		"project_description": "A web application for task management"
	}
}
```

This creates all standard files with sensible defaults.

### Manual Setup

Create files individually:

#### 1. Contract File (index.md)

```json
{
	"tool": "create_or_update_index",
	"arguments": {
		"content": "This project is a task management application.\n\n## Key Sources\n- API docs in docs/api/\n- Architecture in docs/architecture/",
		"replace": true
	}
}
```

#### 2. Project Status (STATUS.md)

```json
{
	"tool": "update_project_status",
	"arguments": {
		"status": "Project setup complete, beginning development",
		"health": "green",
		"changes": ["Initialized project structure", "Set up MCP integration"]
	}
}
```

#### 3. Roadmap (ROADMAP.md)

```json
{
	"tool": "add_roadmap_milestone",
	"arguments": {
		"title": "v1.0.0 MVP",
		"description": "Initial release with core features",
		"target_date": "Q1 2025",
		"deliverables": ["User authentication", "Core API", "Basic UI"]
	}
}
```

## Setting Up docs/

### Create Documentation Index

```json
{
	"tool": "create_doc",
	"arguments": {
		"path": "README.md",
		"title": "Project Documentation",
		"content": "Welcome to the project documentation.\n\n## Contents\n\n- [Architecture](./architecture/) - System design\n- [API](./api/) - API reference\n- [Guides](./guides/) - User guides",
		"category": "reference"
	}
}
```

### Create Category Indexes

For each subdirectory:

```json
{
	"tool": "create_doc",
	"arguments": {
		"path": "architecture/README.md",
		"title": "Architecture Documentation",
		"content": "System design and technical decisions.\n\n## Documents\n\n- [Overview](./OVERVIEW.md) - High-level design\n- [Components](./COMPONENTS.md) - Component breakdown",
		"category": "architecture"
	}
}
```

## File Purposes

### .project/ Files

| File           | Purpose                                  | When to Update            |
| -------------- | ---------------------------------------- | ------------------------- |
| `index.md`     | Define how agents interpret your project | Project structure changes |
| `BACKLOG.md`   | Queue future work (hundreds OK)          | Planning sessions         |
| `TODO.md`      | Dashboard of active work                 | Auto-generated by sync    |
| `ROADMAP.md`   | Long-term plans and milestones           | Quarterly planning        |
| `STATUS.md`    | Current project health                   | Daily/weekly              |
| `DECISIONS.md` | Architecture decisions                   | When making choices       |

### docs/ Structure

| Directory       | Purpose         | Content Examples                |
| --------------- | --------------- | ------------------------------- |
| `architecture/` | System design   | Component diagrams, data flow   |
| `api/`          | API reference   | Endpoints, parameters, examples |
| `guides/`       | How-to guides   | Getting started, tutorials      |
| `reference/`    | Technical specs | Configuration, file formats     |
| `releases/`     | Version history | Release notes, changelog        |

## Best Practices

### Directory Naming

- Use lowercase with hyphens: `user-guide.md`
- Or UPPERCASE for standard files: `README.md`, `CHANGELOG.md`
- Be consistent within each directory

### README.md Files

Every directory should have a README.md that:

1. Explains the directory's purpose
2. Lists all documents with descriptions
3. Links to related documentation

### Cross-References

Link between documents:

```markdown
See [Architecture Overview](../architecture/OVERVIEW.md) for system design.
```

### Timestamps

Include last-updated timestamps:

```markdown
---

_Last Updated: January 2026_
```

## Migrating Existing Projects

### From Unstructured Docs

1. Create the directory structure
2. Categorize existing docs
3. Create README.md indexes
4. Add cross-references

### From Other Systems

1. Export existing content
2. Use `import_tasks` for task lists
3. Manually create roadmap from plans
4. Document decisions retroactively
